## Snapshot write route

The inherited contract defines what the single immutable snapshot must contain and the exact path it occupies. It does not name a transport. Write it with `git` against the checked-out working copy:

```bash
git add providers/claude/snapshots/YYYY/MM/YYYY-MM-DDTHH-mm-ssZ.json
git commit -m "Add Claude risk snapshot YYYY-MM-DDTHH:mm:ssZ"
git push origin HEAD:main
```

Use `git push origin HEAD:main` as the first choice, not as a fallback after another route fails.

Two observed failure modes must not be mistaken for a terminal publication failure:

1. The GitHub contents API may reject the write with `403 Resource not accessible by integration`. The MCP/REST token available to a scheduled run is not guaranteed to carry write scope for this repository. That 403 says nothing about whether `git push` will succeed. It is not evidence of a durable permission problem, and it is not grounds to abandon the run or to report a permissions defect.
2. `git push origin main` may be rejected as `non-fast-forward` even when the push is a genuine fast-forward. Verify with `git merge-base --is-ancestor origin/main HEAD`. If that succeeds, the rejection is not a real ref condition; push with the explicit `HEAD:main` refspec.

If the remote has genuinely advanced, fetch and rebase the single snapshot commit onto the updated `main`, then push again. The snapshot is a new file at a unique path, so it never conflicts with another provider's commit.

## Publication reporting

Report a publication failure only after `git push origin HEAD:main` has actually been attempted and a read-back of the exact target path confirms the snapshot is absent.

The commit must contain exactly one added file under `providers/claude/snapshots/**` and nothing else. Verify this before pushing.

## Unchanged obligations

The idempotent publication retry policy is unchanged and applies to whichever route is used:

- confirm the target path does not already exist before the initial write;
- reuse the identical validated path and identical JSON payload on every retry;
- never regenerate the timestamp, rename the file, alter wording, or change assessment values to obtain acceptance;
- read the exact target path back after any ambiguous or failed write, and treat matching existing content as success;
- a platform safety-classifier or policy block remains non-retryable, and the write route must not be varied to evade one.

All provider ownership, public-safety, and scheduling-immutability rules from the inherited contracts remain in force. A scheduled run still creates exactly one immutable snapshot and then stops.

This repository file only makes v1.2.1 available. It does not activate the prompt in the external scheduler; scheduler migration is a separate explicit operation after review.
